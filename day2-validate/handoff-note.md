# Handoff note

Scenario A · ServiceSG enquiry response. All data is synthetic and labelled as made up.

---

## What it does

An officer opens a shared inbox of eight resident enquiries. In AI draft mode the system shows a drafted reply with inline citations for each enquiry. The officer clicks a citation chip to see the exact policy passage, edits the draft if needed, and approves. In Snippet mode there is no AI — the officer composes a reply from a folder of nine canned snippets instead. A 10-minute session clock applies mild time pressure. A results screen compares the two modes on time to decision, citations opened, words changed and whether a planted error was caught.

The prototype is two files (`index.html` and `data.js`) and a README. No server, no API key, no AI model called. Double-click `index.html` to open.

---

## What is synthetic

Everything. Nothing in this prototype comes from a real resident, officer, case or government record.

- **Four policy pages** — Senior Activity Pass, Community Hall booking, minor home repairs, lost item claims. Each has a `lastReviewed` date. pol-001 is deliberately stale (15 Jul 2026, more than 90 days ago).
- **Eight enquiries** — standard draft, low confidence, image handoff, planted error, multi-topic, escalation, follow-up with prior correspondence, lookup failure. Every sender name is labelled "(synthetic)."
- **Nine canned snippets** — one (snip-03, renewal fee) is deliberately stale.
- **Drafts** — scripted in `data.js`, not generated by a model. Each draft line carries a citation pointer and a confidence flag.
- **Tone guide, escalation list, topic list** — all made up.
- **The planted error** — enq-06's draft says $5 renewal fee; the cited passage says renewal is free for residents aged 70 and above. This is the core test instrument.
- **Measurement data** — timings, citation counts and word-change percentages exist only in memory and reset on page reload.

For a pilot, the policy pages and enquiries would come from real (anonymised) data, the drafts would come from an AI model with retrieval, and the measurement data would be persisted.

## What is missing for production

| Missing | Why it matters |
|---|---|
| Real AI model and retrieval | Drafts are scripted, not generated. The prototype tests the officer's behaviour, not the model's output. |
| Backend and persistence | All state resets on reload. Officer edits, approvals and measurement data are lost. |
| Authentication and roles | No login, no access control, no audit trail of who approved what. |
| Image and attachment reading | enq-04 is a manual handoff. 1 in 5 enquiries has an image, capping AI coverage at 80%. |
| Automated tests | No test file. The only way to verify the prototype works is to open it and click through. |
| Accountability design | No incident path: who owns a wrong reply (stale page, bad draft, rushed approval) is undecided. The chief executive sponsor required this before a pilot. |
| Volume and performance | Eight enquiries. A real inbox has hundreds. The DOM is rebuilt from scratch on every interaction. |
| Mobile layout | Desktop only. |
| Multi-language support | English only. |

## Decisions an engineer must not change without asking

These are design choices that encode business rules, validation logic or stakeholder commitments. Changing them silently would invalidate the test or break an agreement.

1. **Officer-in-the-loop.** The system never sends a reply without an officer approving it. This is the core safety contract. Do not add auto-send, batch-approve or skip-review.

2. **No draft without a citation.** If the policy lookup fails, the officer sees a warning and writes the reply manually. The system never shows a draft that cites no policy page. This is a business rule, not a bug.

3. **The planted error and its threshold.** enq-06's $5 fee vs the cited passage saying free over 70 is the instrument that tests assumption 2. The error is deliberately not flagged low-confidence. Do not fix it, flag it, or remove it — the test passes only if the officer catches it by reading the citation.

4. **The three kill-switch thresholds.** Planted error approved, more than 60% of words rewritten, any draft approved with zero citations opened. These thresholds were agreed with the frontline director. Change them only with her sign-off.

5. **The escalation list.** Law enforcement, legal, regulator, complaints about staff, appeals, vulnerable-resident flags. Enquiries matching any category get no AI draft and go to a human lead. The list came from the skill file and cannot be shortened without policy review.

6. **The head-to-head design.** The same enquiries answered in both modes, with a parallel planted error (stale snippet snip-03 mirrors the stale citation). The head of product required this to justify the cost of citation-grounded drafting over a cheaper text-expander.

7. **Fee and date accuracy rule.** State a fee or date only if the cited passage states it. If the passage is silent, write "please confirm with [team]." Do not guess, interpolate or round.

8. **The 10-minute clock.** Mild time pressure is part of the test design. Removing the clock or making it longer changes what the test measures. The frontline director set this based on realistic queue pressure.

## Handoff decision: keep prototyping

**Decision:** Do not move to a production spec yet. Run the test sessions first.

**Why:** The prototype is built and instrumented, but no officer has tested it. The validation brief says "No sessions run yet." The four riskiest assumptions — officers trust cited drafts, citations catch stale-page errors, cited drafts beat snippets, officers read before approving — are untested. The kill switches exist but have never fired on real tester behaviour. Writing a production spec now would be specifying a system whose core value proposition is unvalidated.

**What to do next:**

1. **Run at least one test session** with an officer (or a realistic proxy) using the 10-minute clock. Answer the same enquiries in both modes. Copy the results into `validation-brief.md`.
2. **Read the kill switches.** If any fires — planted error approved, draft rewritten, rubber-stamping — that is a stop signal. Understand why before deciding whether to iterate or abandon.
3. **Fix the planted-error/lookup-failure conflict first** if testing the planted error matters in this session. enq-06's draft is currently hidden by the forced lookup failure. Either toggle the failure off for that enquiry or add a non-fee planted-error enquiry.
4. **Then decide.** If the assumptions hold, write the production spec using `living-prd.md` as the starting point. If a kill switch fires, the prototype tells you exactly what failed and why — that is what it was built to do.

The prototype is a measuring instrument, not a first draft of the product. Use it to measure before you build.
